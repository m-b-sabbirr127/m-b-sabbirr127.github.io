    Phase 01 Foundations

    Programming Foundations

    I began with pure C, focusing on pointers, memory layout, structs, and manual resource handling. That discipline made the jump to C++ natural: classes, references, RAII, and the standard library without losing low level clarity. Along the way I built strong habits around control flow, debugging with print statements and gdb style thinking, and writing code that other people (and future me) can actually read. Bash became a daily tool for small automations, path management, and build related scripts so the terminal felt like a real workspace instead of a black box.

    Mastery90%
    C C++ Bash Memory Model Debugging Control Flow
    Phase 02 Core CS

    Data Structures and Algorithms

    This phase is the backbone of everything else. I worked through arrays, strings, linked lists, stacks, queues, trees, heaps, and graphs with a focus on when each structure is the right tool. Asymptotic analysis stopped being abstract theory and became the first filter for any solution: time limits, memory caps, and growth rates decide the design before a single line is written. Python helped me prototype ideas quickly and verify correctness on small cases. Java reinforced object oriented structure and cleaner class based designs. C++ remained the language I trust when performance and tight control matter. The real skill was learning to move from a correct slow solution to a correct fast one without losing the original insight.

    Mastery85%
    Arrays and Strings Trees and Graphs Greedy Python Java Big O Problem Decomposition
    Phase 03 Contests

    Competitive Programming Arena

    Contests turned theory into pressure tested skill. On Codeforces I regularly take Div 2, Div 3, and Div 4 rounds, training under time limits and learning to read constraints carefully before coding. BeeCrowd gives structured practice on implementation accuracy, string handling, and foundational dynamic programming. Toph adds regional style problems and archive challenges that mix classical graph algorithms with careful I/O. The obsession is correctness first, then speed. Edge cases, overflow, empty inputs, and maximum values are treated as part of the specification, not afterthoughts. After every contest I upsolve: reopen the problems I missed, study better solutions, and write down the lesson so the same mistake does not repeat.

    Mastery78%
    Codeforces BeeCrowd Toph Edge Cases Fast I/O Upsolving Time Limits
    Phase 04 Frontend

    Web and Frontend Stack

    I learned to ship real interfaces, not just algorithm solutions. Semantic HTML5 gives structure and accessibility. Modern JavaScript and TypeScript handle interactivity and safer logic. TailwindCSS lets me move from idea to polished layout quickly without fighting custom CSS for every component. React powers component based UIs, and Next.js enters when a framework and routing are useful. Public demos keep me honest: a mini social feed model, an agricultural GPA and marks calculator for 2025 criteria, and a playtime or session counter. Each one forced responsive design, form handling, and clean DOM updates. The goal is not flashy UI for its own sake, but interfaces that stay readable, usable on mobile, and easy to maintain.

    Backend, Cloud and Databases

    Frontend alone is not enough. I started building the other half of the stack: APIs with Node.js and FastAPI, simple auth and data flows with Firebase, document storage with MongoDB, and relational modeling with MySQL. Deployment is part of the skill, not an afterthought. I care about clear request and response shapes, sensible error handling, and choosing the right store for the job instead of forcing every dataset into the same pattern. This phase connects algorithmic thinking to real services that other people can call and rely on.

    Engineering Notes

    Short principles I keep coming back to while solving problems and writing code. Click the copy icon on any card to quote it.

    01

    Read the constraints twice

    Most wrong approaches die when you actually respect N, time limit, and memory. Constraints are the first design input.

    02

    Brute force is a teacher

    A correct slow solution often reveals the pattern for the fast one. Don’t skip it when the problem is new.

    03

    Name things for the next reader

    Future-you is a stranger. Clear variable and function names pay off the moment a bug appears at 2 am.

    04

    Edge cases are the real test

    Empty input, maximum values, single element, and duplicates, treat them as part of the specification, not as afterthoughts.

    05

    Upsolve like it matters

    A contest without review is entertainment. The permanent skill gain happens when you reopen the problem after the timer.

    06

    Ship small, learn fast

    Small public tools and clean repos teach more about real engineering than unfinished “perfect” side projects.

    Approach

    Working Principles

    Correctness First

    Prefer a correct solution over a clever one. Edge cases are part of the specification.

    Measure Complexity

    Time and memory bounds guide design. Profile before optimizing hot paths.

    Readable Code

    Clear structure and naming so solutions remain maintainable after the contest ends.

    Iterate Deliberately

    Upsolve, refactor, and document lessons. Progress compounds with consistent review.

    Process

    Problem-Solving Workflow

    The steps I follow on every problem, from reading the statement to reviewing the final solution.

    01

    Understand

    Read the statement twice, note constraints, and work through the samples by hand.

    02

    Plan

    Start from a simple brute force, then find the pattern or data structure that removes the bottleneck.

    03

    Implement

    Write clean C++ with clear naming, using STL where it keeps the solution short and safe.

    04

    Test

    Check edge cases, minimum and maximum inputs, and compare against the brute force.

    05

    Upsolve

    Review failed attempts, study better solutions, and document the lesson learned.
